--- GROUP OBSERVATIONS (ghm-ops) ---
**This group is the kernel, not playbooks.** All seven ghm-* skills map cleanly onto kernel verb behavior, confirming the v2 blueprint's "ghm-* operators map to KERNEL VERB behavior" directive: gate-check → `check`; id-register → the universal plane write-path; sot-builder → plane schema extension; harvest → memory ingestion at cycle close (`learn`/`build` boundary); status-sync → state projection; self-install + template-sync → one manifest-driven `init`/upgrade verb. None should become optional playbooks — they are invariants every loop pass relies on.

**Strongest distilled-experience material** (in rough order): (1) ghm-gate-check's `references/gate-criteria.md` — ~27 named failure patterns with minimum-count floors per gate; it converts almost verbatim into the v2 policy packs and is the group's richness centerpiece; (2) ghm-id-register's Relationship Type Vocabulary + confidence ladder — together they *are* the edge schema and evidence model of the five-plane memory; (3) ghm-harvest's three-way sort + contamination-stripping discipline — the compaction policy that keeps the planes clean; (4) ghm-sot-builder's purity litmus test, <20% self-doc cap, and Context Efficiency Rule — the context-economy doctrine underlying the whole system.

**Duplication is systemic and mostly solvable by pointing at machine-readable sources that already exist.** The prefix→file mapping appears in 4+ places while `domain-profile.yaml` is already canonical; the never-touch list is specified twice (differently) while `install-manifest.yaml` is already canonical; verdict bands appear in 3 places while `readiness.py` is already canonical; the SoT entry format appears in 3 skills. v2 should make every skill *read* the manifest/profile/scorer and delete the prose mirrors — ghm-gate-check's own "do not hand-roll checklists; the scoring engine is the single source of truth" rule, applied group-wide.

**Two internal contradictions to resolve in v2**: (a) ghm-template-sync hardcodes the file lists that ghm-self-install explicitly forbids hardcoding — self-install is the newer pattern, so the merged init/upgrade verb should be manifest-driven and the version-pinned lists retired; (b) the never-touch boundaries of the two installers disagree on `epics/*` — the manifest should carry one authoritative list.

**Model-era scaffolding pattern**: each older skill (harvest, id-register, status-sync, gate-check) carries a references/examples.md that restates its SKILL.md at ~60–70% overlap, plus per-step checkbox lists and defensive instructions ("cite verbatim, do not improvise"). The two newest skills (self-install, and gate-check's scorer delegation) show the target shape: thin orchestration over deterministic scripts, with the distilled judgment kept as compact policy tables. Consolidation should preserve every asset flagged MUST-NOT-LOSE above into policy packs (gate criteria), the plane schema reference (edge vocabulary, confidence ladder, purity rules), and kernel policy (harvest sort, upgrade tiers, projection rules) — and let the step-by-step spoon-feeding go.
